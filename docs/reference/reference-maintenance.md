# Maintaining generated reference and documentation checks

AQ keeps its command and settings lists useful by deriving them from the same
source that the running application uses. This avoids a second, hand-maintained
list of flags or YAML fields slowly drifting away from the code.

## What these checks cover

Three small, local checks cover different kinds of documentation maintenance:

| Check | Source of truth | Output or failure |
|---|---|---|
| CLI inventory | Live Click command tree | [CLI command inventory](cli-command-inventory.md) and its JSON artifact |
| Configuration schema | `AppConfig` plus the editor schema builder | [configuration-schema.json](configuration-schema.json) |
| Page links and catalogs | Markdown headings/links plus the ownership manifest | Missing files, GitHub anchors, or module catalog rows |

For example, after adding a setting, a contributor can refresh only the
stable schema artifact and inspect the page that describes the setting:

```bash
python scripts/generate-config-schema-inventory.py
python scripts/check-docs.py docs/reference/reference-maintenance.md
```

The first command rewrites `docs/reference/configuration-schema.json`; the
second exits zero only if the selected page's relative links and anchors
resolve. It does not start AQ, connect to the database, or edit a local
operator configuration file.

## Focused verification

Run checks against the pages or catalog shard you changed. This is suitable for
a documentation ticket and does not require the application test suite:

```bash
# Verify stable generated facts have been committed.
python scripts/generate-cli-command-inventory.py --check
python scripts/generate-config-schema-inventory.py --check

# Verify a page (or a directory) uses valid GitHub-relative links and anchors.
python scripts/check-docs.py docs/reference/reference-maintenance.md

# Verify every production module assigned to one subject has a linked row.
python scripts/check-docs.py --module-coverage cli
```

The final documentation acceptance owner may use `--all` and
`--module-coverage all`; ordinary authors should not use those broad checks as
a substitute for the page and shard they own. The coverage manifest is
generated by [`refresh_inventory.py`](../plans/documentation-overhaul/refresh_inventory.py),
which assigns each tracked file and records non-production categories with a
reason. It remains the only ownership list.

## Regeneration and ownership

The configuration artifact is generated from
[`src/config_editor.py`](../../src/config_editor.py), the same schema returned
by `aq system config schema`. The CLI artifact is generated from the live Click
tree by [`scripts/generate-cli-command-inventory.py`](../../scripts/generate-cli-command-inventory.py).
Regenerate either artifact in the same change that alters its source, then run
its `--check` form.

`docs/plans/documentation-overhaul/module-ownership.json` is different: the
foundation/acceptance documentation shard owns its large snapshot, so ordinary
authors run `refresh_inventory.py --check` but do not regenerate it merely
because their branch adds a file. A production module is covered when its
assigned catalog contains a relative Markdown link to that exact source path;
private helpers still receive individual rows.

## Failures and recovery

| Symptom | Meaning | Recovery |
|---|---|---|
| `target does not exist` | A relative path is wrong or the destination was renamed. | Correct the link relative to the source page, or restore the intended target. |
| `anchor ... does not exist` | A GitHub heading slug changed. | Link to the current heading or restore a stable heading. |
| `missing linked row` | A tracked production module has no catalog entry in its owning shard. | Add a row to that shard with a relative source link and its component page. |
| `inventory is stale` | A source/schema change was not regenerated into its committed JSON. | Run the named generator and include the output in the same commit. |
