# Dashboard v2 + Work Pipeline Design

**Date:** 2026-08-21
**Status:** Approved (brainstorm with Jack, this doc is the validated design)

## 1. Goals

- A mobile- and desktop-friendly dashboard organized as a single top-down control surface:
  chat with the supervisor as the landing page, a live pan/zoom work graph as the command
  center, and all curation (playbooks, profiles, config) collapsed into Settings.
- Live visibility: agents visibly move between tasks as they are assigned; in-progress
  tasks show spinners; completed tasks show a clear indicator plus summary, commit hash,
  and optional PR link.
- A **bulletproof routing layer**: tasks are created without agent/model/effort
  assignments and cannot start until a triage step assigns them. No LLM in the control
  path — LLM judgment lives in agents; the framework only validates.
- Policy-derived review: per-task and/or per-branch review stages, spawned automatically,
  gating downstream work until approved and merged. Reviewers can merge PRs.
- Interactive spec development with the supervisor, staged ingestion of approved specs
  into tasks, with a human-approved "unleash" transaction.
- Consistent with the standing rule: **no built-in agents; everything through the tmux
  session system. The framework never calls an LLM itself** — agents do LLM work and
  iterate against deterministic validation tools.

## 2. Non-goals / deferred

- Sub-agent visibility (agents spawning sub-agents in the console view) — later phase.
- Mid-task workspace acquisition by agents — rejected for v1 (reintroduces deadlock risk
  that Workspaces v2 eliminated). Escape hatch: agent creates a follow-up task.
- Restructuring the Workspaces v2 schema — simplification is delivered via defaults and
  routing, not schema churn.
- Removing `config.chat_provider` — it remains the utility-LLM config for the supervisor
  runtime and legacy compiler until compilation moves to agents (Phase 6).

## 3. Two state machines, kept separate

**Task execution lifecycle (fixed, universal):** `DEFINED → READY → ASSIGNED →
IN_PROGRESS → … → COMPLETED/FAILED`. Never configurable, never extended by this design.
No new statuses are added anywhere in this spec.

**Work progression pipeline (configurable, per project):** stages like triage, review,
merge are *not* states — they are graph structure: stage-tasks plus gates, generated by
declarative policy rules. "Work that cannot start yet" is always "a task with an open
gate", and the graph shows why. Agents never understand the pipeline; they only see READY
tasks matching their profile. The policy determines what becomes READY, when.

**Clarifying notes (2026-08-21 review):**

- **Stage state is derived, never stored.** No task column records "current stage".
  A work item's pipeline position is derivable from surrounding rows: open gates (with
  type/source/resolution), stage-task edges, and the event history. The pipeline engine
  is **stateless** — it reacts to events and asserts graph structure idempotently; there
  is no per-item step pointer to drift or reconcile after crashes or manual edits.
- **One pass per task.** A task traverses the lifecycle exactly once; each stage is its
  own task making its own single pass. A completed task never re-enters READY because of
  process (e.g. "in review") — COMPLETED always means "an agent finished executing this".
  The only loop-back is explicit rework via `reopen_with_feedback`, which leaves an audit
  trail; a fresh completion event then legitimately fires fresh pipeline reactions
  (idempotency keys are per-event).
- **Enum-shrink direction (later phase, not this wave):** the current 11-state enum
  contains process states smuggled into the mechanical lifecycle (`AWAITING_APPROVAL`,
  `AWAITING_PLAN_APPROVAL`, arguably `WAITING_INPUT` and the `BLOCKED` status). The
  long-term direction is to collapse these into `DEFINED/READY` + gates, shrinking the
  enum toward pure mechanics. New code should not lean on the process-flavored states.

## 4. Pipeline policy layer (`kind: pipeline` playbooks)

Pipeline policies are playbooks — reusing vault storage, hot reload, scoping, the
compiled-JSON store, and run records — with a constrained, deterministic execution model.

### 4.1 Authoring and compilation

- Frontmatter: existing playbook fields plus `kind: pipeline` and `role: <name>`
  (e.g. `role: default-pipeline`).
- The markdown's fenced JSON/YAML block **is** the node graph (harness-file pattern).
  Parsed deterministically — no LLM, no agent, byte-exact, instant. Prose documents
  intent for humans.
- Compile-time validation (extends `CompiledPlaybook.validate()`): pipeline playbooks may
  contain only `action` nodes and structured (dict) transitions. Prompt nodes, LLM
  transitions, and non-whitelisted commands are rejected. Invalid compile → previous
  version stays active (existing rule).

### 4.2 `action` node type (new)

```json
{
  "command": "ensure_task",
  "args": {"project_id": "{{event.project_id}}", "dedup_key": "triage-open", "...": "..."},
  "output": {"as": "triage"},
  "on_success": "next_node",
  "on_failure": "fail_node"
}
```

Executed by the runner via `CommandHandler.execute()` directly — **no `supervisor.chat()`,
no LLM at runtime**. Template substitution (`{{event.*}}`, `{{node_outputs.*}}`) reuses
the existing `runner_context.py` mechanism. `for_each` over a prior node's list output is
allowed (deterministic iteration).

### 4.3 Command whitelist (initial)

`create_task`, `ensure_task`*, `add_dependency`, `gate_create`, `gate_resolve`,
`list_tasks`, `get_downstream_tasks`*, `task_batch_commit`* (spec §8), `edit_task`.
(* = new commands, §10.)

### 4.4 Idempotency

- Each pipeline run records `(playbook_id, event_id)` under a unique constraint —
  duplicate or replayed events cannot double-fire a pipeline.
- `ensure_task(dedup_key, …)` is find-or-create: returns the existing open task matching
  the key (scoped to project) or creates it. Powers triage-batch coalescing and
  per-branch review tasks. `add_dependency` is already idempotent (composite PK).

### 4.5 Scoping and precedence

Existing playbook scoping applies (system / project). New rule for pipeline playbooks
only: a project pipeline playbook with the same `role` as a system one **shadows** it —
projects replace the default pipeline rather than adding alongside it.

### 4.6 Ordinary playbooks: compilation moves to agents (Phase 6)

The LLM markdown→JSON compiler (`compiler.py` `create_chat_provider` path) is removed
from the framework. Vault watcher enqueues a **compile task**; a tmux agent produces the
compiled JSON iterating against a new `aq playbook validate <file>` command (structured
errors from `CompiledPlaybook.validate()`), then installs via a command that re-validates
server-side. Until a compile succeeds, the previous compiled version stays active.
Trade-off accepted: compilation becomes async (agent latency); playbook edits are rare
and not latency-sensitive. Pipeline playbooks are unaffected (deterministic parse).

## 5. Routing (triage)

- Tasks are created `DEFINED` with a **`routing` gate** attached (existing gate
  machinery; the `is_blocked` projection keeps them from READY). No new lifecycle state —
  "unrouted" is a gate badge.
- Default pipeline rule on `task.created`: attach routing gate; `ensure_task` an open
  **triage task** for the project (batch = all unrouted tasks accumulated since the last
  triage run). The triage agent is a normal tmux agent with a curated profile.
- The triage agent assigns, per task:
  1. `profile_id` — from the curated profile set,
  2. `intelligence_class` — from the curated class set (omitted → profile default),
  3. target repo — **iff** the profile has `needs_workspace: true` and the project has
     more than one repo workspace.
- A new `task_route` command validates all assignments against the closed sets
  (profile exists; class exists and has a mapping for the profile's provider; target
  resolves to a project workspace) and resolves the routing gate. Structured errors on
  failure — the correction loop is agent-side.
- **Invariant: nothing reaches READY without being resolvable** (profile + class +
  target-if-needed). Enforced by the gate, verified again at launch.
- Stall guard: a routing gate open past a policy timeout raises a `human` gate.
- When nothing in the curated sets fits, the triage agent may **propose** a new profile
  (draft markdown in the vault) gated on human approval — the curated set grows
  deliberately.

## 6. Intelligence classes

Curated vault markdown: `vault/intelligence-classes/<name>.md`.

- **name** + **description written for the classifier** (e.g. "mechanical transcription,
  single-file edits, known recipe" vs "cross-cutting design judgment").
- Fenced mapping block, provider-agnostic → concrete:

```json
{
  "anthropic": {"model": "claude-haiku-4-5", "thinking": "off"},
  "openai":    {"model": "gpt-5.5-mini", "reasoning_effort": "low"},
  "google":    {"model": "gemini-2.5-flash", "thinking_budget": 0}
}
```

- Tasks carry `(profile_id, intelligence_class)`. Resolution happens at session launch:
  profile → harness → provider → class mapping → `model_flag` value + thinking config.
  Harness schema grows a small seam for expressing thinking level per CLI (markdown
  config, not framework code).
- Profiles gain `default_class` and `needs_workspace` (bool, optionally read-only vs
  writable). Profiles remain **workplace-agnostic**: they declare the *shape* of
  workspace need, never a specific repo.
- Model drift is fixed in the mapping, not per task; classifier prompts stay stable
  because they consume class descriptions, not model names.

## 7. Review (policy-derived)

Review stages are pipeline rules; the framework never learns the word "review".

- `scope: task` rule — on `task.completed` (with a branch): spawn a review task
  (`discovered-from` edge to the reviewed task; **not** parent-child, whose release
  semantics fire too early), profile/class per policy; attach a `task` gate on all
  downstream dependents (`get_downstream_tasks`).
- `scope: branch` rule — `ensure_task` one final-review task per branch (dedup key =
  branch name); as per-task reviews spawn, add `blocks` edges from them to the final
  review. The final review unblocks only when all per-task reviews complete; it owns
  merge authority (its profile's toolset includes PR merge; worker profiles' do not).
  Downstream work carries `pr-merged` gates (existing type, auto-resolved by the sweep).
- Projects compose stages freely: zero for a docs repo, task+branch+security for prod.
- Completion metadata: `aq task close` requires `--summary` (and commit hash is captured
  from the branch) for repo-profile tasks; `pr_url` already exists on the task model.

## 8. Specs: interactive development + staged ingestion

- **Specs live in the vault** (`vault/projects/<pid>/specs/*.md`) with frontmatter
  `status: draft | approved`. Developed *conversationally with the supervisor* — the
  supervisor session edits the file; the dashboard renders it live (work-preview
  component). No new framework machinery for authoring.
- **Approval #1 (spec content):** chat command or button flips frontmatter to approved →
  emits `spec.approved`.
- **Pipeline-driven ingestion (rules in the default pipeline playbook, shadowable per
  project):**
  1. `spec.approved` → `ensure_task` an ingest task (spec-ingest profile; born unrouted
     like everything else).
  2. The ingest agent reads the spec *and the live graph* and emits
     **`task_batch_propose`**: a validated proposal — tasks + typed edges (including
     edges onto existing tasks), cycle-checked, stored as a unit with provenance to the
     spec. Proposals are not tasks: triage doesn't fire, agents can't see them.
  3. `proposal.ready` → policy raises a `human` gate for batch approval (a sandbox
     project may instead auto-commit).
  4. Gate resolved → **`task_batch_commit`**: atomic creation of real tasks + edges
     (server-side re-validation: targets exist, no cycles), tagged `discovered-from` the
     spec. Born unrouted → triage → agents unleashed. Or discard; nothing happened.
- **Preview + revision:** the Command Center renders the proposal as a **ghost overlay**
  (dashed nodes/edges) on the live graph. The user edits the proposal directly
  (retitle, reprioritize, delete, rewire) or asks the supervisor to revise (re-runs the
  ingest agent with feedback; proposal updates in place).

## 9. Dashboard

### 9.1 Information architecture (left nav collapses to four)

1. **Chat** (landing) — supervisor conversation via the same `message_send` →
   supervisor-session path Discord uses (one brain, two surfaces). Replies stream over
   the existing WS (`message.sent`). System activity (task started, review spawned, gate
   waiting) appears as compact event cards inline in the transcript — the supervisor
   narrates inner workings. Phone-first layout: input + status strip.
2. **Command Center** — §9.2.
3. **Work** — flat filterable task/agent tables + task detail (Events/Sessions leave
   top-level nav; events feed chat + graph, sessions are reached via agents).
4. **Settings** — playbooks, profiles, intelligence classes, workspace kinds, config.

### 9.2 Command Center

- **Project strip:** one compact card per project (running agents, blocked/ready counts,
  open gates). Multi-selectable — the canvas renders the selected projects, and
  cross-project dependency edges render when both ends are visible.
- **Canvas:** pan/zoom DAG (React Flow or similar; server supplies nodes/edges, client
  lays out). Task nodes: status color, spinner ring (IN_PROGRESS), completion flash +
  green state, priority as border weight/badge, gate badges (routing ⏳ / review 🔍 /
  pr-merged 🔀). Edge styles by dep type. Ghost overlay for proposals (§8).
- **Agents as avatars** docked to the task they're working; assignment animates the
  avatar traveling to the node. Driven entirely by existing WS events (`task.started`,
  session/agent events, `task.created`, `task.blocked/unblocked`).
- **Mobile:** degrades to project strip + status-grouped card list; canvas available in
  landscape but not the phone-first surface.

### 9.3 Click-throughs

- **Task → sidebar** (mobile: bottom sheet): description, status history, routing chips
  (profile/class), gates with inline resolve for human gates, dependencies; on
  completion: summary, commit hash, PR link.
- **Agent → panel with live tmux console:** existing
  `GET /api/sessions/{id}/stream` SSE (transcript + peek frames) gains a pane-view mode
  (styled peek buffer, pause/scroll) reusing `useTranscriptStream`.

### 9.4 Work preview

Server endpoint lists a task's workspace/worktree diff (names + stats) and serves file
contents read-only (path-restricted to the task's workspace, size-capped). Sidebar
renders markdown properly; the same component previews specs, playbooks, and profiles in
Settings.

## 10. New surface inventory

Commands: `ensure_task`, `get_downstream_tasks`, `task_route`, `task_batch_propose`,
`task_batch_commit`, `aq playbook validate`, spec approve (frontmatter flip + event).
Events: `spec.approved`, `proposal.ready` (plus existing `task.*`, `gate.*`).
Schema: `action` node type + pipeline validator; playbook `kind`/`role` frontmatter;
pipeline-run idempotency key; proposal storage; profile `default_class` /
`needs_workspace`; intelligence-class vault documents; harness thinking-level seam.
Dashboard: nav collapse, chat page, Command Center canvas, sidebars, console pane-view,
work preview, settings curation pages.

## 11. Error handling principles

- Pipeline action failure → run failed + `playbook.run.failed`; surfaced via supervisor
  narration in chat and a warning badge on the graph. Retries are manual — no
  self-healing magic in the control path.
- Validation commands return structured, agent-legible errors; correction loops are
  always agent-side, the framework only judges.
- Stalled gates (routing or otherwise) escalate to `human` gates on policy timeouts —
  silent stalls become visible questions.

## 12. Phasing (each phase ships working software)

1. **Control plane core:** `kind: pipeline`, action nodes + validator, `ensure_task`,
   `get_downstream_tasks`, idempotency, role shadowing; default pipeline = routing gate +
   triage task; `task_route`; intelligence classes; profile `default_class` /
   `needs_workspace`. Proof: bulletproof routing E2E with existing claude/codex agents.
2. **Review policy:** task- and branch-scope rules, merge authority, `pr-merged` gating,
   close-with-summary enforcement.
3. **Dashboard shell:** nav collapse, chat page wired to supervisor sessions, mobile
   layouts.
4. **Command Center graph:** canvas, live agents, sidebars, project strip + multi-select.
5. **Observability:** console pane-view, work preview endpoint + markdown rendering.
6. **Spec ingestion + compiler-as-agent:** proposal/commit commands, spec-ingest profile,
   spec lifecycle rules in the default pipeline; move ordinary-playbook compilation to a
   tmux agent + `aq playbook validate`.
7. **Later:** sub-agent visibility, class-mapping tuning, inter-project rendering polish.

## 13. Testing

- Control plane: unit/integration — validator rejects non-deterministic nodes; duplicate
  event fire is a no-op; routing invariant ("never READY unrouted") under concurrent
  creation; ensure_task race safety; batch commit atomicity + cycle rejection.
- Dashboard: component tests for graph/chat; visual states driven by recorded WS event
  fixtures.
- E2E: aq-live-test rig with real tmux agents — scripted scenario: create 5 tasks →
  triage routes → work completes → reviews spawn → branch review merges → downstream
  unblocks. Mobile viewport smoke via browser tooling.
