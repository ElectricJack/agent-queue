# aq CLI audit — 2026-09-08

The CLI is broadly operational, but task creation has confirmed usability and scripting defects. The audit found **318 core commands**, verified **232 autogenerated command dispatches**, exercised **29 successful live read operations**, and obtained **538 passing tests** across the CLI/API-contract and task-creation suites, including a targeted environment retry.

This is an investigation and report, not a repair release. No application code was changed. The exact originally failing task-creation command/error was not supplied, so the findings below identify reproducible causes rather than claiming a definitive diagnosis of that specific attempt.

## Why adding a task can fail

### 1. Partial flags unexpectedly enter the wizard and lose supplied values — confirmed

`src/cli/tasks.py:282` takes the noninteractive path only when **project, title, and description are all truthy**. Otherwise it fetches projects and runs the complete wizard. It does not pass the supplied project/title as defaults, despite help saying those flags skip wizard steps.

Reproduction:

```bash
aq task create -p my-project -t "Fix login" --priority 50 --type bugfix --integration-mode direct
```

Because the description is absent, this asks for project and title again. The captured request in [create-reproductions.json](create-reproductions.json) demonstrates the effect: supplied `flag-project`, `Flag title`, priority `50`, `bugfix`, and `direct` became the mock wizard's `wizard-project`, `Wizard title`, priority `100`, `feature`, and `pull_request`. These are captured CLI requests with the network mocked, not changes to real tasks.

A noninteractive caller can therefore encounter a prompt instead of creation; an interactive caller can create with unintended settings. Profile, agent type, intelligence class, parent, root, reason, and deliverables have separate forwarding logic; they should not be lumped into the confirmed lost fields.

**Current workaround:** supply all three primary values:

```bash
aq task create --project my-project --title "Fix login" \
  --description "Reproduce the login error and correct its cause." \
  --priority 50 --type bugfix
```

This avoids the wizard. It is a syntax workaround, not a claim that every project/routing/authorization combination will accept creation. Worker filings additionally require a held task and `--reason`; idle sessions and out-of-scope requests are intentionally refused.

### 2. Single-task creation ignores `--json` — confirmed

```bash
aq --json task create -p my-project -t "Fix login" -d "Investigate login"
```

With a successful mocked daemon response, stdout was:

```text
Task created: audit-mocked
  Mock title
```

Exit status was zero, but stdout was not JSON. A script parsing the response can fail **after a task was successfully created**. Retrying such a command blindly can create duplicates. The single-task path prints directly; graph creation uses `emit()`. Evidence: `src/cli/tasks.py:339`, [create-reproductions.json](create-reproductions.json).

### 3. Startup opens the plugin database even for help — confirmed, environment-sensitive

Importing `src.cli.app` calls `_load_plugin_cli_groups()`, which calls `_load_plugin_config_from_db()` before Click handles the requested command. That helper uses `PluginClient.connect()`, whose PostgreSQL adapter calls `initialize()` and schema setup.

Under the original restricted sandbox, `aq task create --help`, `aq --help-all`, `aq status --json`, and `aq test ...` stalled before useful command execution. A ten-second Python traceback localized the wait to `app.py`'s plugin-config startup path. The stalled commands later emitted an asyncio executor warning mentioning a 300-second join timeout. Outside the sandbox, help and live reads completed. This demonstrates startup's dependency on database connectivity; it does **not** demonstrate that the operator's unrestricted shell always hangs.

References: `src/cli/app.py:349–395`, `src/cli/client.py:451`, `src/database/adapters/postgresql.py:145`. No operator migration command or schema repair was run. The fact that ordinary CLI startup reaches an initialization path is itself a design concern: help/discovery should not require database initialization.

## Prioritized repair backlog

1. Fix task-create partial flags: preserve supplied values, prompt only for missing values, and give noninteractive callers a clear usage error instead of unexpectedly entering the wizard. Add regression coverage for partial project/title/description and integration/priority/type overrides.
2. Make single-task creation emit machine-readable success under `--json`; then standardize envelopes across autogenerated and handwritten commands. Test successful output as well as error output.
3. Remove database initialization from CLI import/help discovery. Load plugin configuration lazily through an appropriate read path with a bounded timeout.
4. Update installed aq skills and the CLI module guide: current spellings, global flag placement, close outcomes, worker filing permissions, current profiles, and auth behavior.
5. Resolve the advertised-but-unimplemented `ask-human` command; retain `plugin logs` only as an explicitly documented compatibility notice or retire it deliberately.
6. Add missing creation input coverage (`requires_kinds`, priority validation), and maintain a test that compares handwritten CLI options against intended backend capabilities.

These are proposed repair items in this report, not newly queued daemon tasks. The scope interpreted “sweep ... all the command line tools” as testing/auditing the aq CLI.
