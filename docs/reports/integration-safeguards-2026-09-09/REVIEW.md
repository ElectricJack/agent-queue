# Tiered integration safeguards: simplification review

Reviewed 2026-09-09 against main e44fce88. Recommendation for discussion; no runtime protections or configuration changed. No CI or tests run for this review.

## Recommendation

Keep tiered branches and batch integration. Remove the requirement that every tier reproduce a complete release protocol. Default to fast development: workers publish work, parents assemble it, a root batch gets focused validation, and AQ promotes or parks it. Make full CI and separate reviewer agents configurable quality policy. Preserve the few controls that prevent concurrent overwrites, lost work, and accepting a result for the wrong commit.

The main problem is coupling: task completion, branch ownership, session lifetime, review approval, parent generations, repair episodes, CI receipts, and cleanup all constrain one another. A correct manual merge can satisfy the user's objective while failing AQ's historical sequence. Removing one refusal at a time would leave that coupling intact.

Highest-value changes:

1. Add first-class adoption of work already delivered by an operator, and cancellation that preserves uncertain evidence without holding the entire project.
2. Remove mandatory full CI and a dedicated verifier at every intermediate parent; permit focused checks at the root boundary and optional full CI.
3. Replace persistent role-to-role branch handoffs with short mutation ownership where feasible. Reclaim stopped writers automatically after preserving their work.
4. Park a failing batch/member and keep independent work moving. Serialize main publication, not the entire life of every batch.
5. Replace exact historical receipt-chain requirements with source/result commit evidence plus a small delivery manifest. Keep audit history without making every historical identifier an eligibility dependency.
6. Decouple task organization from frozen Git topology; ordinary reparenting and administrative acceptance should not require rebuilding the old execution episode.

This is a recommendation to delete requirements and state transitions, not add another large collection of override flags.

Both recorded repair stages expired with **zero counted attempts**. This proves wall time can exhaust the episode without counted attempts; it does not prove that no worker activity occurred.
- Live Agent Queue status summarized 191 `active_owner`, 16 `missing_receipt`, 6 `stale_review`, 3 `human_hold`, 2 `open_child`, and 1 `pending_ci` entries. Matter Engine had 20 `active_owner` and 11 `open_child`, with no active batch. No throughput benchmark was run. Priority estimates below are architectural judgments supported by incidents, not measured percentage speedups. ## What the smaller system should look like

Worker publishes an immutable commit → parent assembler includes it in a manifest → root builder makes a candidate → selected validation runs → one publisher advances main → task delivery projections catch up asynchronously.

Planning hierarchy remains useful, but not every parent needs its own release ceremony. Quality choices belong in one project policy, with an effective-policy display. Suggested development defaults: no dedicated reviewer/verifier for ordinary children, optional parent checks, focused root validation, full CI asynchronously, automatic stopped-writer preservation/recovery, and failed batches parked without blocking independent work. Repository-host protections still apply.

Only four conditions should normally demand operator intervention: an active writer that cannot be stopped/fenced safely; conflicting remote changes that cannot be reconciled; a required dependency/product decision; or repeated repair failure beyond the cost budget. A missing historic receipt should first trigger reconciliation.

Proposed operator interface (not commands that exist today): adopt delivered work, cancel-and-preserve, retry from current head, and retarget future delivery. These should show the observed ref/SHA and record the choice in one action. Avoid a universal `--force` that also discards dirty work or bypasses concurrent-writer exclusion.

## Implementation order

1. **Unstick current delivery:** implement operator adoption and cancel-and-preserve; distinguish detached/stopped/live owners; reconcile the three current tickets and the held batch through those actions. Acceptance: manually merged work closes without inventing old CI or replaying its old task branch.
2. **Cut serial quality overhead:** one explicit development policy consumed by collection, parent completion, CI, and root promotion. Remove mandatory intermediate verifier/full CI. Acceptance: a multi-level task tree reaches one root boundary with focused local validation and accurately reports optional full CI as pending/skipped.
3. **Fix automatic recovery and queue progress:** pause repair effort clocks during waits, automatically preserve/reclaim stopped work, park failed batches, and continue independent members. Acceptance: the zero-attempt timeout case recovers and a bad batch cannot indefinitely starve unrelated ready work.
4. **Reduce durable-state coupling:** simplify receipt manifests, ownership roles and unexecuted reservations; separate hierarchy organization from delivery. Keep old tables read-only during migration if needed, then retire obsolete transitions and tests that only enforce the removed protocol.
5. **Delete legacy support and polish:** remove unused App attestation path after checking installations, obsolete SQLite rollout text, manual snapshot rerun instructions and misleading status terminology. Do this after the new fast path works, not as a prerequisite.

Changes should have focused tests for competing writers, crash-after-push, preservation of dirty work, already-delivered adoption, parked-batch progress, and stale validation identity. Use real isolated PostgreSQL/daemon tests for state-machine changes. Do not build a new exhaustive permutation suite for every removed bookkeeping invariant.

## Decisions worth making before implementation

My recommendation is to accept occasional development-main regressions in exchange for focused checks and fast repair, while retaining exact write exclusion and preservation of work. Keep mandatory full CI for release/protected branches or explicitly strict projects. If that tradeoff is accepted, it should become AQ's ordinary development path, not a special emergency override that agents are reluctant to use.

The first three implementation phases produce the practical speedup. A full rewrite of every integration table before delivering them would repeat the current problem.
