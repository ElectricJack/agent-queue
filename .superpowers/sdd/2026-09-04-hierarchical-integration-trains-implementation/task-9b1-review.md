### Issues

#### Critical (Must Fix)

1. **Candidate Git writes are not protected by current lease, revision, or branch-owner authority.** `src/integration/candidates.py:129-158` takes one state snapshot and then performs clone/fetch, construction, push, and PR creation after that transaction has ended. `_locked_state` first locks the batch row and only later takes the hierarchy lock (`src/integration/candidates.py:391-413`), reversing Task8's hierarchy-first order, and it checks only the lease's batch/repository identity, not its owner, fence, expiry/reconciliation state, or `integration_branch_owners` (`src/integration/candidates.py:434-450`). Subsequent member/final/PR writes are unconditional on the batch still being the current revision and the caller still owning the branch (`src/integration/candidates.py:609-623`, `src/integration/candidates.py:666-672`, `src/integration/candidates.py:694-723`). A repair dispatch can therefore hand the exact integration branch to an attached repair delegate, or a concurrent rebuild can advance `current_revision`, while an older build continues writing and pushing and finally resets the shared batch lifecycle to `testing`. This violates the single-writer fence and the required second authority revalidation before persistence or remote mutation. Acquire the hierarchy lock before resource rows, carry an explicit lease/branch-owner fence in the command, and revalidate project mode, designated repository, batch/current revision, root operation/current stage, lease owner/fence, and branch owner immediately before every progress CAS and external ref/PR mutation. Require affected-row success, and prove/perform the repair-owner handback before candidate construction resumes.

2. **Repair acceptance bypasses both the reserved-path boundary and Task7's writer authority.** Reserved source changes are converted into an ordinary conflict (`src/integration/candidates.py:544-551`), but `_valid_repair_lineage` explicitly accepts an added path when the resolved blob equals the source blob and never re-runs the reserved-path guard (`src/integration/candidates.py:791-826`). Thus a repair commit that adds the exact rejected `.codex/settings.json` (or another daemon-owned path) is accepted and later published. More generally, `accept_repair` trusts caller-supplied operation/stage/OIDs, checks only that the named stage row is active, and never proves the current Task7 repair task/session/workspace/fence or an immutable resolution reservation (`src/integration/candidates.py:268-389`). `_conflict` also hardcodes stage 0 and dispatches stage 0 (`src/integration/candidates.py:738-766`), so a conflict on a rebuilt candidate after escalation cannot be accepted by the actual current debug stage. The test hides the production object/authority gap by directly pushing the repair commit into the daemon's retained store (`tests/test_integration_candidates.py:559-560`). Consume an authoritative Task7 resolution reservation/result bound to the current batch/revision/ordinal/operation/stage and live writer fence, import/fetch its exact OIDs through a daemon-owned channel, reject reserved paths across both the member delta and repaired range, and transfer ownership back before advancing the cursor. Add primary/debug, adversarial-content, reserved-path-repair, stale-rebuild, and real workspace-to-daemon object-transfer tests.

#### Important (Should Fix)

1. **The non-empty production publication path can silently skip publication and bypass Task9a authentication/repository binding.** `app_client` and `forge_provider` are optional, and `_publish` returns a successful built result when either is absent (`src/integration/candidates.py:106-126`, `src/integration/candidates.py:626-631`); the one-member test codifies this incomplete success (`tests/test_integration_candidates.py:481-500`). Initial clone, wildcard fetch, and remote-ref proof use generic Git against caller-resolved `repository.url` (`src/integration/candidates.py:902-919`, `src/integration/candidates.py:633-635`), whereas Task9a's isolated App-auth primitive is used only for the push. The generic manager path inherits the complete daemon environment (`src/git/manager.py:327-350`), so private-repository reads either fail or consult ambient Git configuration/credentials outside the approved App channel. The supplied App repository is never checked against the frozen batch repository, and the PR response is checked only for head SHA/branch, not repository or base (`src/integration/candidates.py:647-665`). Make daemon-owned, exactly repository-bound App and forge providers mandatory for every non-empty build; add isolated authenticated exact-repository fetch and ref-read primitives; reject client/repository mismatch; and validate/persist the PR's repository, number, base, branch, and head.

2. **Publication replay is not durably reconciled after the PR boundary.** The only persisted PR field is `integration_batches.pr_url` (`src/database/tables.py:1938-1940`), and any non-null URL causes `_publish` to return without rechecking the remote ref or audit PR (`src/integration/candidates.py:629-631`). The crash test's forge fake keeps its in-memory result across service reconstruction (`tests/test_integration_candidates.py:368-385`, `tests/test_integration_candidates.py:625-665`), so it does not model daemon restart or prove that create-before-persist cannot duplicate a PR. Persist the typed PR identity plus candidate-ref publication state before/after each boundary, reconcile the exact remote ref and existing PR on replay, and use a durable forge idempotency identity rather than provider-process memory.

3. **Candidate/rebuild Git inputs are not the sealed authoritative inputs.** Clean construction invokes `merge-tree current reviewed_head` without the member's sealed `source_base_sha` (`src/integration/candidates.py:552-559`), while identity validation only proves the two commits exist and the head tree matches (`src/integration/candidates.py:838-846`). If Git's inferred merge base predates or differs from the sealed source base, the squash includes history outside the reviewed member delta. Separately, `rebuild` accepts any syntactically valid caller-provided `new_base_sha` and supersedes the old revision before proving that OID is the designated repository's current default-branch head or even exists (`src/integration/candidates.py:160-227`); a nonexistent or foreign local OID strands the batch on N+1 and reports `base_moved` only afterward. Apply the exact `source_base_sha..reviewed_head_sha` delta (and prove the required ancestry/tree relationship), and derive/verify the rebuild base through the authenticated frozen repository/default-branch authority before pinning and atomically superseding N.
