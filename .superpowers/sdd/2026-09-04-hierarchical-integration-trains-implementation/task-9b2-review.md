# Task 9b2 implementation review

## Spec compliance

- **FAIL — Critical 3, Important 3, Minor 1.** The implementation establishes a strong typed preparation/finalization skeleton, but the root-main claim is not isolated from the existing candidate observer, ambiguous prewrite claims can be re-executed, and moved-main intents cannot reach the required superseded/rebuild transition. The schema and finalizer also do not fully preserve the required immutable receipt authority on SQLite or verify the complete frozen member set.

## Strengths

- Preparation derives batch, revision, candidate SHA, aggregate evidence, project lease, branch fence, operation/stage, publication, and ordered receipt IDs from hierarchy-locked state rather than caller inputs (`src/integration/main_promotion.py:88-273`). The recovery ref is pinned before the intent, reservations, mutation claim, and `testing -> promoting` transition are committed together (`src/integration/main_promotion.py:105-273`).
- The actual write uses the Task 9a App-auth exact-OID primitive with an explicit expected-old SHA, and local fast-forward proof precedes it; there is no forge merge API, synthetic commit, or post-main CI call (`src/integration/main_promotion.py:365-395`).
- Exact trusted aggregate success is projected in the same locked transaction that revalidates the candidate subject (`src/integration/ci.py:371-469`). Public command arguments are limited to batch/revision, session principals are denied, and service/playbook authority is checked before entry (`src/commands/integration_commands.py:338-365`).
- Root receipt insertion, lifecycle updates, and outbox insertion are in one hierarchy transaction, and the crash hook test correctly demonstrates rollback of a mid-receipt failure (`src/integration/main_promotion.py:587-734`, `tests/test_integration_main_promotion.py:647-677`). The child finalizer now explicitly rejects root intents (`src/integration/promotion.py:1057-1062`, `src/database/queries/integration_delivery_queries.py:429-430`).

## Issues

### Critical

1. **The generic candidate observer can consume a `root_main` claim without advancing its root intent, permanently stranding a successfully pushed promotion.** `CandidateService._observe_unresolved_mutations()` selects every reserved mutation, and its desired-remote path calls `_reconcile_observed_mutation()` without filtering purpose (`src/integration/candidates.py:2178-2209`, `src/integration/candidates.py:2211-2257`). With the new `root_main` purpose, a crash after the external main push but before `RootPromotionService._mark_applied()` lets a concurrent/public candidate build mark the claim `applied` and continue. The root intent remains `prepared`; later root reconciliation sees the already-applied claim and returns early without changing the intent (`src/integration/main_promotion.py:474-513`), after which the root finalizer rejects the non-`pushed` intent (`src/integration/main_promotion.py:611-621`). This violates exclusive root reconciliation and the required push/receipt crash recovery. Restrict candidate observation/mutation to candidate-owned purposes; treat every unresolved `root_main` intent/claim as a blocker and let only `RootPromotionService` atomically record root applied proof plus intent state. Add a real cross-service crash test: push main, crash before proof, call public `CandidateService.build/rebuild`, then root-reconcile to exactly one full receipt set.

2. **A prewrite-marked ambiguous claim is CAS-taken and blindly pushed after expiry.** `_claim_execution()` rotates any expired reserved nonce without checking `prewrite_at` (`src/integration/main_promotion.py:397-438`), while `_mark_prewrite()` deliberately preserves an existing marker with `coalesce` (`src/integration/main_promotion.py:440-472`). The submitted test codifies the unsafe behavior: after crashing immediately after the prewrite marker, a fresh service waits only until claim expiry and then performs the push (`tests/test_integration_main_promotion.py:458-489`). In production, the marker means the prior Git write may still be in flight or its response may be lost; the prescriptive ruling requires this state to remain ambiguous and forbids blindly repeating it. Make expired takeover conditional on `prewrite_at IS NULL`; a marked claim must authenticate main and either finalize proven candidate/descendant or return `reconciliation_blocked`. Also require a fresh sufficient execution horizon before marking prewrite. Test an actually unresolved/in-flight prior writer rather than using a crash hook that proves no push occurred.

3. **External movement of main leaves the current root intent permanently blocking the required N+1 rebuild.** For a current revision whose authenticated main is neither expected old nor candidate/descendant, reconciliation only returns `base_moved` and leaves both intent and mutation reserved (`src/integration/main_promotion.py:323-357`). `_supersede_unattempted()` refuses unless `current_revision` has already changed (`src/integration/main_promotion.py:515-545`), but the reviewed rebuild path refuses to change it while any reserved mutation exists (`src/integration/candidates.py:329-350`). The supersession test bypasses this cycle by directly writing `current_revision=1` (`tests/test_integration_main_promotion.py:542-558`), so it does not exercise the public protocol. Reconcile the current, expired, exact, prewrite-null claim to `superseded` under the hierarchy lock before returning `base_moved`, then allow `CandidateService.rebuild()` to create N+1; a live claim waits and a prewrite/unknown claim remains blocked. Add a public promote-to-base-moved -> expiry -> reconcile -> rebuild test with no direct database revision mutation.

### Important

1. **Authenticated descendant reconciliation has no authenticated object import, so normal production history cannot prove ancestry.** The service reads the remote OID through the App client, then immediately runs local `merge-base --is-ancestor` against the retained store (`src/integration/main_promotion.py:317-328`, `src/integration/main_promotion.py:785-795`). A later human/main commit will normally be absent from that store, yielding Git status 128 and `reconciliation_blocked` even when the tested candidate is an ancestor. The test hides this by making `PushGit.arun_git_result()` return ancestry from an in-memory tuple without importing an object (`tests/test_integration_main_promotion.py:228-241`, `tests/test_integration_main_promotion.py:630-644`). Reuse the Task 9a isolated App-auth exact-OID fetch/import path, pin the authenticated observed OID, and only then run real ancestry proof. Test with real local Git objects where the descendant is initially absent from the retained store.

2. **The root finalizer does not verify that reservations are the complete exact immutable batch/revision member set.** It checks only that reservation ordinals are contiguous and ordinal zero matches the intent receipt (`src/integration/main_promotion.py:596-621`); it never locks/compares `integration_batch_members` and `integration_candidate_member_results`, nor checks reservation batch/revision/source/review/result fields against the intent and frozen rows. The new table likewise has only an `intent_id` FK and a separate result FK, so a reservation can attach intent A to batch/revision B or freeze mismatched source/review identity (`migrations/versions/d4a81f0c9e72_root_main_promotion_intents.py:253-287`). That falls short of the explicit complete-member verification requirement and allows a structurally valid partial/misbound receipt set to be committed. Add an intent-to-(batch,revision) composite FK (and the needed referenced uniqueness), strengthen member identity structurally where practical, and have finalization compare the full ordered reservations against locked sealed members/results before any receipt. Add missing-ordinal, extra-row, cross-intent batch/revision, and mismatched frozen-identity tests on both dialects.

3. **The SQLite upgrade drops the pre-existing append-only guards on delivery receipts.** Adding the root tuple/FKs through `batch_alter_table("task_delivery_receipts")` recreates the SQLite table (`migrations/versions/d4a81f0c9e72_root_main_promotion_intents.py:209-229`), but this migration neither drops nor recreates `trg_task_delivery_receipts_update/delete`. The earlier migration that altered this same table explicitly recreated append-only guards after its batch operation (`migrations/versions/e4c6a8b20d31_parent_collection_and_review_evidence.py:359`); PostgreSQL ALTER preserves them, so the new head has dialect-skewed immutability. Preserve/recreate the receipt guards around both upgrade and downgrade batch operations, and assert UPDATE and DELETE fail after SQLite and PostgreSQL U-D-U cycles. The current migration test only checks table/column presence (`tests/test_migration_root_main_promotion.py:27-47`).

## Assessment

**Task quality: Needs fixes.** The implementation has sound preparation, authority derivation, exact-push, and transactional-outbox foundations, but the current claim/reconciliation state machine is not safe or live across the required crash and main-movement boundaries. The schema/finalizer gaps also prevent trusting root receipt immutability and completeness across both supported dialects.
