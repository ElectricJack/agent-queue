# Task 10b implementation review

## Spec Compliance

- ❌ **Issues found (1 Critical, 4 Important, 1 Minor).** The implementation has strong fail-closed trust and currentness machinery, but its workflow can suppress all full CI for an ordinary fork PR, its hosted verifier rejects a valid shared-suite attestation, its provider publication is not exclusive under concurrent fresh services, the production root-promotion command does not receive the configured App client, and proof construction can combine a strictly selected payload with the ID of a different malformed record.
- ⚠️ **Approved limitation retained:** ordinary task PRs still use the full-CI fallback because authenticated focused-check transport is not yet present (`task-10b-brief.md:141-142`). Task 11 still owns the real App/check identities, trust installation, workflow variables, protection/probe checks, and activation; no live cutover is authorized by this task.

## Strengths

- Candidate evidence is re-derived under hierarchy-first authority and binds the active project, designated repository, exact batch/revision, root operation/stage, candidate head, publication, ordered check set, producer, and conclusive green evidence (`src/integration/attestation.py:327-435`). Provider and Git work occurs outside that transaction, followed by an exact state comparison before a proof is returned (`src/integration/attestation.py:90-159`).
- Trust is loaded from the authenticated candidate tree and is bound to both canonical and numeric repository identity (`src/integration/attestation.py:240-280`). Provider clients are keyed by the exact immutable repository binding (`src/integration/attestation.py:282-300`).
- The provider observer validates exact check names, producer, head, conclusions, workflow attempt identities, and suite coverage, and emits canonical typed payloads (`src/integration/ci.py:780-857`). The selector excludes post-main lifecycle states (`src/database/queries/integration_reconciliation_queries.py:124-133`).
- Worker session construction removes the entire daemon-only Integration App credential prefix even when a harness tries to restore it (`src/sessions/env.py:96-99`, `src/sessions/env.py:226-233`).

## Issues

### Critical (Must Fix)

1. **A fork PR can suppress its only full-CI run by choosing the reserved-looking branch prefix.** `.github/workflows/tests.yml:102-111` suppresses the three full jobs for every pull request whose `head.ref` starts with `aq/integration/`; it does not require `head.repo.full_name == github.repository`, an exact daemon-produced integration-ref identity, or any corresponding trusted base-repository push. An untrusted fork can therefore open an ordinary PR from `aq/integration/x`; the fork push is not the matching base-repository integration push, but the base PR event runs no full suite. This violates the required ordinary-PR full-CI fallback and the “matching integration PR” qualification (`task-10b-brief.md:139-142`). The test only searches workflow source substrings and has no same-repository/fork truth table (`tests/test_integration_workflow.py:154-163`). **Minimal remediation:** suppress a PR run only for a provably matching same-repository integration publication (at minimum exact same-repository plus the reserved deterministic ref contract; preferably exact durable publication identity). Add behavioral truth-table cases for a local matching integration PR, a fork PR using the prefix, and an ordinary PR.

### Important (Should Fix)

1. **The hosted decision rejects valid required checks that share one GitHub Actions check suite.** `scripts/check-integration-attestation.py:97-138` collects one suite ID per check and requires all of those IDs to be unique at line 136. Multiple matrix check runs from one Actions workflow legitimately share a check suite. The canonical producer model intentionally permits this: it requires unique check IDs/names, deduplicates suite IDs, and maps all checks to the matching workflow attempt (`src/integration/ci.py:102-118`, `src/integration/ci.py:791-830`). Thus a valid canonical payload for the three required matrix checks can publish successfully but will always make the main-push script return false, defeating the requested trusted skip. **Minimal remediation:** remove per-check suite-ID uniqueness while retaining unique check-run IDs/names and exact coverage by the set of unique suites; test the three exact required checks sharing one suite/workflow attempt as well as genuinely duplicate check identities.

2. **Concurrent fresh publishers can create more than one canonical attestation, including after promotion has begun.** `IntegrationAttestationService.publish` performs an unlocked read-before-create (`src/integration/attestation.py:107-121`), and `AuthenticatedGitHubObserver.publish` repeats the same list-then-POST sequence without a durable reservation or provider idempotency key (`src/integration/ci.py:859-916`). Two services can both observe no record and both POST. The post-network state check at `src/integration/attestation.py:139-140` can make a caller stale, but cannot undo the extra provider record; promotion may consume the first record before the second POST completes, violating one canonical proof/no duplicate and the prohibition on publication after main starts (`task-10b-brief.md:100-105`, `task-10b-brief.md:158-160`). A focused in-memory barrier diagnostic against the production observer produced two successful POSTs from two concurrent calls. Existing replay tests are sequential (`tests/test_integration_attestation.py:393-453`). **Minimal remediation:** add a durable exclusive publication claim/reservation bound to the exact subject and evidence, acquired/revalidated in short hierarchy-first transactions around provider I/O, with invalidators blocked while live and lost-response reconciliation after expiry. Prove two fresh service instances make exactly one POST and that main cannot cross a live publisher.

3. **Production root promotion is constructed without the configured GitHub App client.** Core creates `integration_app_client` only as a local closure and passes it to the attestation service (`src/orchestrator/core.py:1477-1494`); it never exposes the client/factory used by the command path. The command fallback instead reads nonexistent `orchestrator.integration_app_client` and passes `None` (`src/commands/integration_commands.py:283-297`). `RootPromotionService.reconcile` then deterministically returns `configuration_blocked` (`src/integration/main_promotion.py:337-356`). Consequently a correctly configured production daemon can publish/resolve evidence but cannot perform the root main write. The wiring test verifies only candidate handler and resolver ownership, not production root-promotion construction (`tests/test_orchestrator.py:77-92`). **Minimal remediation:** give root promotion a repository-bound production client factory (or otherwise construct its exact bound client from reviewed config) and test the real command factory with configured and missing App config; the configured case must reach the exact bound client and the missing case must remain fail closed.

4. **Proof construction can attach a malformed record's ID to a different strictly validated payload.** `_trusted_records` uses Python's loose equality for App IDs (`src/integration/attestation.py:460-470`), under which `True == 1` and integer-valued floats compare equal to integers. `_proof_from_records` strictly selects a payload through `select_trusted_attestation`, but independently computes `check_run_id=max(ids)` from that looser record set (`src/integration/attestation.py:472-493`). With one valid record and a higher-ID record whose App ID is a bool/float equal to the trusted integer, the returned payload is valid while the durable proof identity points at the malformed record. Exact provider provenance must fail closed, not splice two records. **Minimal remediation:** have one strict selector return the selected record ID together with its validated payload; require strict positive integer App and record IDs throughout. Add mixed valid-plus-bool and valid-plus-float App-ID cases and assert failure rather than a hybrid proof.
